第一章系统整体架构

ezharness = 基于 ezloop 引擎的桌面 agent harness。启动即对本机全权（文件不限目录 + 原生 shell）。三层结构：desktop（Electron 壳：窗口 / 托盘 / 内嵌浏览器）拉起 core（Go sidecar，gin 三层 MVC + 内嵌前端）伺服 frontend（端无关页面，双入口）；core 也可直接运行——浏览器访问同一份页面（浏览器控制等桌面专属能力自动降级）。

1.1 双仓库：引擎 × 宿主

仓库角色
ezloop
../ezloop 本地 replace		 agent 引擎：core 循环（loop / agent / fork）、provider 三协议（anthropic / openai / responses）、hook / warp 扩展点、ext 通用组件（filetools · skilltool · mcp · approve · askuser · task · offload · contextfix）
ezharness
本仓库		 宿主应用：装配（选 hook、传参数）+ 产品域（会话树 / 设置 / 终端 / 快应用 / 前端）+ 自有 hooks（remind / trim / sessionstore / sysprompt / uploadfile / guard / trace）
hook 分界判据：依赖 session 域状态（Store / 资源基线 / 落盘）的 hook 留 ezharness（remind · trim · sessionstore…）； 纯工具组件下沉 ezloop（filetools · skilltool · mcp · approve…）。skill/mcp 的变更检测因此归 remind——若长在 skilltool/mcp 自己身上，它们就耦合了 session 基线，无法成为 ezloop 公共组件。 开发期 go.mod replace 指向本地 ezloop；发布前升版本、移除 replace。

1.6 应用生命周期

startup
desktop 壳（ezharness.exe · Electron 主进程）
 ├─ 读 ezharness.json         # 应用根（portable 用 PORTABLE_EXECUTABLE_DIR）
 ├─ spawn ezharness-core.exe  # core 退出 → 壳随之退出
 └─ health 轮询就绪           # /api/app/health（30s 超时）→ 主窗 loadURL core 地址

core（ezharness-core.exe · Go sidecar）
 ├─ config.Load()             # 读应用根 ezharness.json（缺失建默认；--root 可覆盖根）
 ├─ newApp(cfg)               # MkdirAll → os.Chdir(数据目录)
 ├─ a.start()                 # net.Listen 预占端口 → buildRouter() → srv.Serve
 └─ 信号等待（Interrupt/SIGTERM）→ stop()
  • buildRouter 换代重建：domain.NewHub()（含 bootstrap 恢复）→ TerminalService → AgentService.Assemble → 全部 controller。设置页改端口 / 数据目录触发换代：shutdownGeneration（杀终端 shell → 取消运行轮并等落盘 → 关 server）→ syncDrained → chdir → buildRouter；boot 代际计数跨代共享，前端据此判断新服务就绪
  • 退出顺序同理：轮内历史只在 OnEnd 落盘，不等落盘直接退出会丢整轮；SSE 长连直接 srv.Close()（优雅 Shutdown 会拖满超时）

第二章session 树

一条 session = 一次会话聚合：内存运行时（domain.Session）+ 磁盘存档（sessions/<id>/session.json）。多个 session 世代构成 session 树（线 → compact 换代链 → fork 分叉），用户在"分支"（线）粒度上切换对话。

2.1 核心概念

概念含义
session 世代一次 compact 归档产生一个新世代；每世代一个 <id>，各自有存档目录
ID（叶）当前叶世代 ID，compact 换代随之更新
RootID（线根）所属分支的稳定身份——Hub.branches 注册表键、前端路由、API :id 参数全用它；换代不换线
线（branch/topic）同一 RootID 下的世代链 + 侧栏条目（topics.json 的 TopicEntry）

2.4 session 树的三种演进

compact 换代 仅用户手动

归档话题：摘要封存旧库、新库带摘要继续。POST /api/topics/compact

compact-flow
BeginArchive 占锁（摘要最长 2 分钟；锁发消息/切分支/二次归档）
→ summarizeMsgs（模型视图，含 marker 摘要链，链式浓缩）
→ 旧库翻 Archived=true 封存
→ sys.Set(base, summaryBlock)        # 新 system 两段生效
→ 新库初始快照先落盘（空 messages + compress 边——任一时刻重启新库都可恢复）
→ SetID(newID)（清基线/用量，LineRoot 留）→ SetPrev → topics.UpdateLeaf（换代不换线名）
→ RotateTo（内存换代：清历史/水位）→ Publish session.compact
与 trim 的分工：trim 是上下文管理（模型侧：水位自动 + trim_context 主动，就地截断不换库）；compact 是会话树管理（用户侧：摘要归档换代）。

fork 分叉 copy 语义

POST /api/sessions/:id/fork body {anchor}——锚点消息序号（含选中消息）。

  • 源是"未产生新消息的 fork"时沿 fork 边上溯到实际内容源（空叉链折叠）
  • 新 session 体内携带 [0, anchor] 完整副本（快照隔离；system / 水位承源）→ topics.Add(Kind:"fork") → LoadBranch + SetActive
  • fork 线标题 = 锚点消息内容（TitleFromMsg）；有自己的首条新增 user 后显式切换
  • 命名规则：new 线 = 首条真实 user（FirstUserTitle 跳过 agent_status / res_change / end_reason / trim marker 等系统注入，40 字截断）；世代名 = 本代首条 user，命名后固定

归档 预留

POST /sessions/:id/archive——仅翻 snap.Archived 位；活动分支当前叶或运行中拒绝（标记会被下次落盘覆盖）。归档世代继续聊走 fork@tip。

三种「分叉」勿混淆：① fork 分叉（copy 语义，复制前缀开新线）；② task 分身（轮内子循环，事件带 ForkID，存档在 forks/ 只存增量，前端分身抽屉展示）； ③ compact 换代（归档封存，同线换叶）。

2.5 生命周期与恢复

lifecycle
创建：newSession（rootID 空 → 自成一根）→ Assemble（装配 wiring；snap 有则还原 SysPrompt）
     ├─ 新线：首条发言时 topics.Add（延迟建索引防空线粉尘）
     └─ fork：创建即 Add

运行：StartRun ⇄ FinishRun 每轮；sessionstore.OnEnd 落盘

恢复（NewHub → bootstrap）：
     ListMain 列目录项（排除 -task-）→ mtime 降序 → LoadSnap 逐个
     → 跳过 Archived → root = snap.LineRoot（空则 RootOf 沿边上溯兜底）
     → newSession + restoreFrom + Register；第一个（最近未封存）为 Active
     restoreFrom 还原：history / Title / ResSnap 基线 / LastOutputAt / Usage / 水位
     （CtxTokens 缺省从历史尾部 agent_status 兜底 LastCtxTokens）/ LineRoot / Edge
     systemPrompt 不重组：快照 base / summary 直接注入（记忆/skill/mcp 变更等下个 session）

切换：Switch 按索引 LeafID 现读快照（按需恢复）；SetActive 不取消旧分支运行轮（后台跑完）

3.2 引擎时序基石：消息何时入史

以下 6 条是理解一切 hook 行为的前提（来自 ezloop core/loop.go，是文档易错点）：

时刻引擎动作
Run 开始构造 LoopState → 应用 RunOption（WithHistory 把 modelView 放进来；WithUploadFiles 写 Metadata）→ 发 loop_start 事件
① input 先入史用户输入 AppendMessage(user) ——先于 startHooks。因此 startHooks 运行时末条必为本轮 input，remind / uploadfile 都靠"插在末条 user 之前"定位轮首
② startHooks 后跑15 个 hook 的 OnStart 按装配序执行：system 注入（sysprompt，ezharness 不用引擎的 systemPrompt 字段）、历史修理、工具注册、轮首消息插入都发生在「system, [history], input」已就位的序列上
③ assistant 入史每次模型响应完成（含 ToolCalls）→ assistant 消息入史 → 发 model_end
④ tool 消息批末入史不是即时入史：同批全部调用执行完后，严格按调用顺序统一写入（Skip 短路的调用也占位）。补全规则：未执行的补 "not executed: <name>"；hook Skip 无文案时引擎默认 "skipped by tool-start hook: <name>"
⑤ OnLoop 回边工具批入史后 → 下次模型调用前。此刻本轮全部工具结果已按序在史、消息序列协议完整——filetools 在这里插图片消息、trim 在这里截断（引擎串行区，无并发竞争）
⑥ OnEnd 收尾defer 语义：成功 / 失败 / 取消 / panic 恢复路径都跑（context.WithoutCancel）→ 发 loop_end。sessionstore 落盘在最后
fork（task 分身）的差异：浅拷贝 Agent 后 startHooks = nil（组装期 hook 不重跑，防重复注入）、systemPrompt = ""（seed 已含完整 system）、toolWarps = nil（传入工具已带主循环 warp 壳）； 继承全部运行期 hook（OnModel* / OnToolStart / OnToolEnd / OnLoop / OnEnd）——审批照拦、session 照存。子 state 设 ForkID（如 task-1）与 SeedLen。

第四章产品视角 · 人机协同交互

agent 的能力边界再大，落到用户手里的只是几个交互面。ezharness 把人机协同交互工具外置——不塞进对话流硬凑，做成独立的产品面，让用户在 agent 工作时能看、能改、能答。核心理念：为用户提供最简单的交互方案——上下文工程、工具封装、人机交互三支柱，能力越复杂，落到用户手里的越要简单。
